# Task OS-009: OpenRouter Specialist Review Matrix Automation

## Summary
Design and plan an automated, multi-model review runner using OpenRouter to orchestrate independent specialist reviews (Claude, DeepSeek, Grok) prior to ChatGPT triage and Codex release gating. The system enforces strict Zero Data Retention (`zdr: true`, `data_collection: deny`), deterministic model selection without auto-routing, domain-based file allowlisting, local pre-send secret scanning, machine-validated structured output, and predictable local artifact storage without human intervention or secret leakage.

## Motivation
The AstraZit Music OS review protocol (`.ai-review/REVIEW_PROTOCOL.md`) establishes a multi-tiered review hierarchy where high-risk changes (T2/T3) require independent reviews from specialist models (Claude, DeepSeek, Grok) before triage by ChatGPT and release gating by Codex. Currently, assembling review packets, selecting domain-scoped files, invoking specialist APIs, sanitizing prompts, and collecting structured findings is a manual, context-intensive process. 

Automating this review matrix through OpenRouter provides:
1. **Repeatable, Auditable Reviews**: Standardized prompt injection, payload minimization, and sequential report collection.
2. **Context Efficiency**: Each specialist receives only the exact domain files and instructions required—never the full conversational history.
3. **Strict Privacy & Cost Guardrails**: Enforcing OpenRouter privacy flags (`zdr: true`), model-specific request tuning, and preflight secret scanning.
4. **Machine-Validated Output**: Eliminating ambiguity by locally validating structured JSON responses before rendering human-readable Markdown.
5. **Separation of Concerns**: Complete independence between specialist evaluations prior to architect triage.

## Scope & Deliverables

### In Scope
1. **Core Review Engine**: A deterministic review runner script (`scripts/review_runner.py`) using Python standard library (Python >= 3.12, no virtualenv required) with a PowerShell 7 wrapper (`scripts/review.ps1`).
2. **Ticket Review Profiles**: Declarative configuration mapping ticket IDs (e.g., `RADIO-003`) to risk tier, specialist assignments, domain-specific file allowlists, and prompt templates.
3. **Deterministic Model Router**: Rigid model dispatch matching exact approved identifiers:
   - `anthropic/claude-sonnet-5` (Documentation, specification, and acceptance consistency)
   - `deepseek/deepseek-v4-pro` (Bash, code, subprocess, and test edge-case correctness)
   - `x-ai/grok-4.6` (Adversarial operational failure modes, recovery, and blindspots)
4. **Sequential Dispatcher**: Dispatches specialists sequentially (`Claude → DeepSeek → Grok`), persisting each result to disk immediately before invoking the next.
5. **Model-Specific Request Adapters**: Dedicated request-body builders accommodating provider quirks (e.g., omitting `reasoning.effort` for Grok 4.6, disabling reasoning for DeepSeek, and configuring bounded reasoning tokens with omitted temperature for Claude in RADIO-003).
6. **Local Pre-Send Secret Scanner**: Dual-layer scanner separating filename/path deny rules from content inspection. Distinguishes actual high-entropy credentials from legitimate placeholders and documentation strings.
7. **Machine-Validated Structured Output**: Enforces local schema validation on specialist responses (verdict, structured findings array, evidence, files reviewed, checks run, risks, next gate) before marking complete. Fails closed on malformed or empty output.
8. **Payload Manifest & Report Storage**: Writing local execution manifests, normalized JSON artifacts, and rendered markdown reports under `reports/reviews/<TICKET>/<RUN-ID>/` (gitignored).
9. **Architecture & Governance Documentation**: Complete specification in `docs/architecture/OPENROUTER_REVIEW_MATRIX.md` and integration references in `.ai-review/REVIEW_PROTOCOL.md`.

### Non-Goals
- Modifying production application code (`apps/radio/`, `packages/schemas/`).
- Auto-remediation, code generation, or automated editing of repository files.
- Staging, committing, or pushing git branches.
- Calling production YouTube APIs or deploying to Linux VPS hosts.
- Printing, logging, or persisting `OPENROUTER_API_KEY`.
- Requiring third-party Python package installations (`pip install`) for the runner core.
- Replacing the final Codex release gate or human approval gate for T3 tickets.

## Security Boundaries & Trust Model

- **Zero Trust on Network Egress**: No payload leaves the local machine without passing strict path allowlists, filename deny rules, and automated secret scans.
- **Runtime Secret Isolation**: `OPENROUTER_API_KEY` is read strictly from the host user environment at execution time; never read from `.env` files in git, never printed, never logged, and never included in error stack traces.
- **Provider Privacy Guarantees**: Every request to OpenRouter explicitly specifies:
  ```json
  "provider": {
    "zdr": true,
    "data_collection": "deny"
  }
  ```
- **Fail-Closed Privacy**: If OpenRouter cannot fulfill the request under ZDR / data collection denial, or if the returned model alias does not match the requested approved model, the review fails immediately.
- **External Controls as Defense-in-Depth**: Observed external OpenRouter controls (workspace guardrails, $5 key limit, $10 workspace limit, model restrictions) are acknowledged as operational guardrails, not permanent guarantees. The runner locally enforces all model and privacy rules.
- **Accepted Trust Boundary Limitation**: Process argv and memory on the local machine are visible to the running user and root. Stream keys and API tokens must never be passed as CLI arguments.

## Python Runtime & Proposed CLI Interface

### Runtime Requirements
- **Python**: `>= 3.12` (compatible with newer supported Python versions).
- **Dependencies**: Standard library only (`urllib.request`, `json`, `re`, `pathlib`, `hashlib`, `os`, `sys`). No virtualenv required for MVP.
- **PowerShell**: PowerShell 7 (`pwsh`). Wrapper dynamically discovers a suitable Python >= 3.12 executable on `PATH` or standard install locations and fails clearly if none exists.

### CLI Usage
```powershell
# Default offline / mock review (Sequential: Claude -> DeepSeek -> Grok; does NOT authorize network dispatch)
.\scripts\review.ps1 RADIO-003

# Validation-only dry-run (assembles payloads, runs path deny checks & secret scan, writes manifest, zero dispatch)
.\scripts\review.ps1 RADIO-003 --dry-run

# Explicit live network review (requires OPENROUTER_API_KEY and human authorization gate)
.\scripts\review.ps1 RADIO-003 -Live

# Run a specific specialist only (offline mock)
.\scripts\review.ps1 RADIO-003 -Specialist claude

# Output directory override
.\scripts\review.ps1 RADIO-003 -Output reports/reviews/RADIO-003/custom-run
```

> [!IMPORTANT]
> **Wrapper Network Execution Semantics**:
> - `.\scripts\review.ps1 RADIO-003` executes an offline mock review and does **NOT** authorize network dispatch.
> - `.\scripts\review.ps1 RADIO-003 --dry-run` performs validation-only payload inspection with zero network dispatch.
> - Explicit live network review strictly requires `.\scripts\review.ps1 RADIO-003 -Live` and remains governed by the human approval gate (GATE-03 / GATE-09).

## Model Matrix & Sequential Dispatch

### Model Configuration
| Role / Domain | Target Model | OpenRouter Model ID | Unique Request Body Requirements |
| :--- | :--- | :--- | :--- |
| **Docs & Spec Auditor** | Claude Sonnet 5 | `anthropic/claude-sonnet-5` | RADIO-003 configuration: `max_output_tokens: 8000`, bounded `reasoning: { "max_tokens": 3000 }`, temperature omitted, enforce ZDR. |
| **Code & Bash Specialist** | DeepSeek V4 Pro | `deepseek/deepseek-v4-pro` | Disable reasoning effort, enforce ZDR. |
| **Adversarial Operations** | Grok 4.6 | `x-ai/grok-4.6` | **Omit reasoning block entirely** (Grok returns HTTP 400 if `reasoning.effort` is present), enforce ZDR. |

*Note*: No OpenRouter auto-router (`openrouter/auto`) or unapproved fallbacks are permitted.

### Sequential Dispatch Flow
1. **Step 1: Claude Sonnet 5**
   - Assembles Claude domain payload.
   - Executes pre-send checks.
   - Dispatches HTTP request; receives structured JSON.
   - Validates schema locally; persists `claude-review.json` and `claude-review.md` immediately.
2. **Step 2: DeepSeek V4 Pro**
   - Assembles DeepSeek domain payload.
   - Executes pre-send checks.
   - Dispatches HTTP request; receives structured JSON.
   - Validates schema locally; persists `deepseek-review.json` and `deepseek-review.md` immediately.
3. **Step 3: Grok 4.6**
   - Assembles Grok domain payload.
   - Executes pre-send checks.
   - Dispatches HTTP request (reasoning block omitted); receives structured JSON.
   - Validates schema locally; persists `grok-review.json` and `grok-review.md` immediately.
4. **Step 4: Finalize Manifest & Summary**
   - Persists `manifest.json` and `run-summary.json`.

*Persistence occurs immediately after each specialist completes.* If a specialist fails or aborts, prior completed specialist artifacts remain intact on disk, and the council is marked `INCOMPLETE`.

## Pre-Send Secret Scanning & Path Filtering

The scanner operates in two decoupled, strict layers:

### Layer 1: Path & Filename Deny Rules (Fail-Closed)
Rejects payload construction immediately if any targeted file matches:
- `*.env*` (e.g., `stream.env`, `.env.local`)
- `*id_rsa*`, `*id_ed25519*`, `*.pem`, `*.key`, `*.pkcs12`, `*.pfx`
- Credentials or token stores (e.g., `credentials.json`, `token.pickle`)

### Layer 2: Content Scanner (Entropy & Pattern Distinction)
Distinguishes actual high-entropy credentials from legitimate documentation and syntax references.

#### Strictly Prohibited (Fail-Closed):
- Actual OpenRouter API keys: regex `sk-or-v1-[a-zA-Z0-9]{64}`.
- Exact match of the runtime value of `$env:OPENROUTER_API_KEY`.
- Actual private key headers: `-----BEGIN [A-Z0-9 ]*PRIVATE KEY-----`.
- Real YouTube stream keys: 4 groups of 4 alphanumeric characters plus a 4-character suffix (e.g., `[a-z0-9]{4}-[a-z0-9]{4}-[a-z0-9]{4}-[a-z0-9]{4}-[a-z0-9]{4}`) where characters are random/high-entropy.
- Actual Bearer tokens: `Authorization:\s*Bearer\s+[A-Za-z0-9\-_\.]{32,}` where the token is not a documented placeholder.

#### Explicitly Allowed (Harmless References & Placeholders):
- The literal string `OPENROUTER_API_KEY` (e.g., variable names, documentation).
- `sk-or-v1-` when used as an example or prefix description in prose/regex.
- Documented placeholders:
  - `Authorization: Bearer <placeholder>` or `Bearer <token>`
  - `STREAM_KEY=<placeholder>` or `STREAM_KEY=xxxx-xxxx-xxxx-xxxx-xxxx`
  - Descriptive mentions and example snippets of `stream.env` (e.g. in `SKILL.md` or architectural prose).

## Machine-Validated Output Specification

Reviewers are instructed to return a strict JSON structure. Local schema validation is authoritative; provider JSON Schema support is treated as an optimization, not a guarantee.

### Required JSON Schema Fields:
```json
{
  "verdict": "PASS | CORRECTION REQUIRED | FAIL",
  "findings": [
    {
      "severity": "P0 | P1 | P2 | P3",
      "file": "path/to/file",
      "line": 42,
      "failure_mode": "Detailed failure description",
      "smallest_correction": "Minimal targeted code or doc fix"
    }
  ],
  "evidence": ["Command output or file snippet"],
  "files_reviewed": ["path/to/file1", "path/to/file2"],
  "tests_checks": ["Static inspection of logic", "Unit test simulated"],
  "risks": ["Identified operational or regression hazard"],
  "next_gate": "CHATGPT TRIAGE | CODEX RELEASE GATE | HUMAN APPROVAL"
}
```

### Local Validation Rules:
1. JSON must parse cleanly without trailing garbage.
2. `verdict` must be one of `PASS`, `CORRECTION REQUIRED`, or `FAIL`.
3. `findings` must be an array of objects conforming to the schema (maximum 5 findings unless P0 blockers exist).
4. `files_reviewed` must match or be a subset of the allowlisted files sent.
5. If validation passes, the runner persists the normalized JSON and renders a formatted `*-review.md` artifact.
6. If validation fails, the specialist is marked `FAILED`, sanitized error diagnostics are preserved in `<specialist>-error.txt`, and the council is marked `INCOMPLETE`. Only sanitized error messages, HTTP status codes, and bounded diagnostics (token metrics, finish reasons, block types) are persisted; raw reasoning, refusal, or message text is never persisted.

## Report Storage & Git Versioning Policy

### Local & Ephemeral by Default
All execution runs write to:
`reports/reviews/<TICKET>/<RUN-ID>/`
- `manifest.json`: Execution metadata, token metrics, file hashes, requested vs returned model IDs.
- `<specialist>-review.json`: Normalized machine-validated output.
- `<specialist>-review.md`: Rendered markdown report.
- `run-summary.json`: Council-wide status and finding aggregations.

### Git Ignore Invariant
- `/reports/reviews/` must be added to `.gitignore`.
- Machine review runs are voluminous, ephemeral, and run frequently during development.
- **Canonical Review Record**: Only after ChatGPT triage and human approval will a concise, canonical summary be deliberately committed to git (e.g., `reports/<TICKET>-review-summary.md` or within the review packet).

## Cost Controls & Retry Semantics

- **Max Output Tokens**: 4,000 completion tokens default (8,000 for Claude Sonnet 5 in RADIO-003 to accommodate bounded reasoning and structured output).
- **Max Payload Size**: 128 KB per specialist prompt payload.
- **Retry Policy**:
  - **HTTP 502 / 503 / 504 (Server Errors)**: Exactly one (1) bounded retry after a 2-second backoff.
  - **HTTP 400 / 401 / 403 / 429 (Client & Rate Limit Errors)**: **Zero retries**. Abort affected specialist immediately and fail closed.
  - **Council Failure**: If any specialist fails, subsequent specialists in the sequence may be halted or marked skipped, and the overall council run is marked `INCOMPLETE`.

## Acceptance Criteria

1. **CLI Execution**: `.\scripts\review.ps1 RADIO-003 --dry-run` discovers Python >= 3.12, validates all path deny rules and pre-send secret scans, and writes `manifest.json` without network egress.
2. **Standard Library Portability**: `scripts/review_runner.py` executes successfully using standard library modules only, with zero virtualenv requirements.
3. **Sequential Execution & Persistence**: Runs `Claude → DeepSeek → Grok` in order, persisting each specialist's normalized JSON and Markdown report immediately upon completion.
4. **Grok Compatibility**: Runner omits `reasoning.effort` for `x-ai/grok-4.6` and succeeds without HTTP 400.
5. **Secret Scanner Precision**: Catches real high-entropy keys, denies `.env` and `.pem` files, while successfully allowing `OPENROUTER_API_KEY` mentions, `sk-or-v1-` prefix prose, and `<STREAM_KEY>` placeholders.
6. **Machine Output Validation**: Locally validates JSON schema; rejects non-conforming, empty, or unparseable output.
7. **Zero Repository Side-Effects**: Running the tool creates no unstaged changes outside `reports/reviews/`, never modifies source code, and never stages or commits.
